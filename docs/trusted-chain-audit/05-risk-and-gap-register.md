# Risk And Gap Register

This document tracks risks that may not appear as simple bugs but can prevent the chain from being industry acceptable.

## Risk Categories

| Category | Description |
|---|---|
| Requirements risk | The system misunderstands, misses, or silently changes original requirements. |
| Traceability risk | Artifacts cannot be reliably traced in both directions. |
| Model risk | UML models are syntactically valid but semantically incomplete or misleading. |
| Code risk | Generated code does not enforce required business behavior. |
| Evidence risk | The platform cannot prove what it generated or why. |
| Human review risk | Ambiguity and low confidence are not routed to humans. |
| Domain risk | The system is applied to regulated or safety-critical domains without the necessary controls. |

## Phase 0 Revalidation

2026-05-24 revalidation confirmed the original risk statuses before implementation. Phase 1 implemented a source-attributed RequirementBaseline and baseline gate. Phase 2 implemented per-requirement coverage and run-level bidirectional traceability for requirement/model/design/code artifacts with backend gates for uncovered accepted requirements, orphan artifacts, fake/shallow traces, and pending design auto-fill. Phase 3 implemented deterministic semantic model-quality gates and preserves non-functional requirements as `not-modelable` review paths when UML cannot directly represent them. Phase 4 implemented requirement-linked code business assertions with completion blocking for failed critical behavior checks. Phase 5 implemented first-class EvidencePackage aggregation, API review decisions, and downstream evidence gates for supplied blocked or failed evidence. Phase 6 implemented backend cross-domain and negative regression coverage. Phase 7 implemented frontend/browser reviewability, evidence export, browser evidence visibility, blocking for failed/pending browser evidence, and Playwright acceptance checks.

## Risks

| ID | Category | Risk | Impact | Current control | Required control | Status |
|---|---|---|---|---|---|---|
| R-001 | Requirements risk | Natural-language requirements may be under-extracted or over-interpreted. | Downstream models and code can look complete while missing user intent. | Phase 1 adds a source-attributed RequirementBaseline, quality report, confidence, status, criticality, assumptions/conflicts containers, and a hard baseline gate for critical quality failures. Phase 3 improved deterministic actor/object extraction so new business-domain terms are not limited to a fixed actor vocabulary. | Human review decisions and richer source provenance are still needed before this risk is fully controlled. | partially mitigated |
| R-002 | Traceability risk | One-way or local traceability may create a false sense of coverage. | Requirements may not be traceable to code/tests, or generated artifacts may lack requirement justification. | Phase 2 control: `CoverageMatrix` and `TraceabilityMatrix` now provide per-requirement coverage and bidirectional requirement/model/design/code links, with orphan, uncovered, fake, shallow, and pending-review diagnostics that can block completion. Phase 4 adds requirement-to-test links for passing business assertions and blocks failed assertion diagnostics. Phase 5 packages the matrix and review decisions into EvidencePackage. Phase 7 verifies traceability visibility and export in the browser. | Future work should add richer reviewer filtering and live generated-app trace views. | mitigated |
| R-003 | Model risk | Non-functional requirements may disappear because they are not directly diagrammable. | Performance, security, usability, reliability, and compliance needs can be lost. | Phase 3 marks non-functional accepted requirements with no model trace as `not-modelable` and adds an `alternative-evidence:<requirementId>` review item instead of silently treating them as covered. Phase 5 carries that item into EvidencePackage and requires a durable review decision before the package can become complete. Phase 7 shows the path in the frontend and verifies export/review by browser. | Future work should attach domain-specific measurement artifacts automatically. | mitigated |
| R-004 | Code risk | Generated code may implement screens without enforcing business rules. | The chain appears successful but fails real workflows. | Phase 4 control: code stage generates requirement-linked business assertions for permissions, roles, state machines, data consistency, boundaries, exception feedback, idempotency, and observable business behavior. Failed critical assertions block completion, and `/BUSINESS_CONTEXT.md` alone is not accepted as behavior proof. Phase 6 regression proves the UI-only negative case, orphan code, and orphan test evidence fail through the expected gates. Phase 7 adds browser-executed representative workflow checks and blocks failed/pending browser evidence from downstream approval. | Future work should run the browser workflow checks directly against every generated application bundle. | mitigated |
| R-005 | Evidence risk | Run results may not preserve enough records for audit or repair. | Reviewers cannot reconstruct why an artifact was generated or which claim is proven. | Phase 5 adds EvidencePackage with baseline, quality report, coverage matrix, traceability matrix, model/code artifact summaries, assertion/test results, browser evidence, review items, review decisions, failure records, and repair logs. Snapshots persist the package and pipelines emit it as an artifact. Phase 7 adds frontend export/review and Playwright screenshot/DOM/console/network artifacts. | Future work should persist browser artifacts from live generated runs automatically. | mitigated |
| R-006 | Human review risk | Low-confidence, conflicting, or automatically completed requirements may continue downstream. | The platform can silently convert uncertainty into false certainty. | Phase 1 blocks conflicting baseline quality reports; Phase 2 blocks pending auto-filled design traceability at backend completion. Phase 5 creates durable API review decisions for conflict, low-confidence, derived assumption, pending-review, not-modelable, partial-coverage, and failed-assertion items, and downstream start routes reject supplied blocked or failed evidence. Phase 7 exposes review items and decisions in the browser and verifies blocked reasons/export with Playwright. | Future work should enrich reviewer identity and approval policy per project role. | mitigated |
| R-007 | Domain risk | Users may overclaim suitability for regulated domains. | Legal, safety, financial, or compliance exposure. | Audit docs define the base scope as ordinary business, teaching, prototyping, and experimental systems, not regulated or safety-critical domains. | Product-facing domain boundary, manual sign-off requirements, and optional domain-specific standards for regulated use. | open |
| R-008 | Browser acceptance risk | The user-facing review flow may not actually expose or enforce trusted-chain gates. | Backend artifacts could exist without reviewers being able to inspect baseline, coverage, traceability, pending decisions, evidence, or blocked-state reasons in the browser. | Phase 7 adds Playwright browser evidence for baseline review, CoverageMatrix, TraceabilityMatrix, pending-review/conflict/low-confidence/critical-partial blocking reasons, evidence export, screenshots, DOM, console, network, and representative generated workflow behavior. | Future work should broaden this to live generated app bundles and more viewport/device coverage. | mitigated |
| R-009 | Model semantic risk | A traced UML model can be syntactically valid but semantically shallow or mismatched. | A reviewer may see green traceability even when the model does not explain the baseline requirement. | Phase 3 adds blocking `semantic-model-gap` diagnostics for requirement/design models and sequence workflows, while ignoring purely structural actor/relationship nodes as sole semantic proof. The 2026-05-24 follow-up tightened behavior requirements so object-only word overlap is insufficient; traced elements must explain the action slot and, when present, the object slot. Phase 6 regression covers seven domains and fake/shallow traceability failing through `semantic-model-gap`. Phase 7 proves the gate evidence is browser-reviewable. | Future work can add richer semantic parsers; deterministic gates remain conservative. | mitigated |

## Gap Evaluation Questions

1. Can a reviewer reproduce a generation decision from source text and run artifacts?
2. Can the platform explain why each requirement was modeled, not modeled, or blocked?
3. Can generated code be inspected by requirement ID?
4. Can tests fail when traceability is forged or shallow?
5. Can non-functional requirements survive the chain even when UML cannot represent them?
6. Can the system stop downstream work instead of generating plausible but unsupported artifacts?
