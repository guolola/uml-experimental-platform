# Recordly 学生入门解说视频制作包

## Summary

本制作包用于录制一段 8-12 分钟的学生入门教程，面向第一次使用 UML 实验平台的学生。视频用“图书馆座位预约系统”跑通从创建项目、选择课程/系统分配的免费托管 Provider、录入需求，到需求规则、需求 UML、设计模型、代码原型和说明书交付的完整链路。

Recordly 仅作为外部桌面录屏和剪辑工具使用，不接入当前 TypeScript monorepo。录制方式采用“短片段录制 + 后期配音 + 预制完成态补拍”，避免模型等待时间打乱节奏。Recordly 项目、音频、导出视频和素材不提交到源码仓库。工具文档参考 [webadderallorg/Recordly](https://github.com/webadderallorg/recordly)。

## Recording Setup

### 本地环境

1. 启动本地演示环境：

   ```powershell
   npm run dev
   ```

2. 如果需要保留运行历史、文档版本和跨次录制状态，改用：

   ```powershell
   npm run dev:postgres
   ```

3. 录制前在浏览器打开本地 Web 地址，确认账号已登录，并从右上角账号入口进入“全局设置”。

4. 在“模型托管配置”选择首个可用托管 Provider，在“默认模型”选择该 Provider 的默认或首个允许模型，点击“测试托管配置”，成功后保存。

5. 创建或准备一个演示项目，确保至少预演完成一次：

   - 需求规则可生成。
   - 需求模型至少有一个 SVG 成功渲染。
   - 设计模型至少有一个 SVG 成功渲染。
   - 代码页预览非空。
   - 说明书能打开编辑器或下载 DOCX。

### Recordly 设置

- Capture：录制浏览器应用窗口，不录整个桌面。
- Audio：正式录屏时关闭麦克风；后期把配音作为额外音频轨导入。
- Cursor：开启平滑光标、点击强调和适度 cursor size。
- Zoom：对“新建项目”“生成需求规则”“智能修复”“模型详情”“下载说明书”等关键操作添加手动缩放。
- Timeline：长等待段只保留 3-5 秒生成任务进度，其余剪掉或用 speed region 加速。
- Export：1080p MP4；保存 `.recordly` 工程以便后续改配音或补镜头。

### 文件命名

- Recordly 工程：`uml-student-onboarding-library-seat.recordly`
- 配音文件：`uml-student-onboarding-library-seat-voiceover.wav`
- 导出视频：`uml-student-onboarding-library-seat-1080p.mp4`
- 如需中间片段：`clip-01-project-create.mp4`、`clip-02-requirements.mp4` 等。

## Demo Content

### 项目信息

- 项目名称：`图书馆座位预约系统`
- 项目描述：`面向学生和管理员的座位预约课程实验，演示需求、UML、设计、代码和说明书全流程。`
- 项目模板：`UML 全流程`
- 可见性：优先选择 `团队成员可见`，没有团队时选择 `仅我可见`。
- 默认模型策略：选择列表中的首个可用托管 Provider。解说统一称为“课程或系统分配的免费托管 Provider”。

### 需求文本

```text
图书馆座位预约系统允许学生登录后查询空闲座位，按日期和时间段提交预约。
系统需要校验登录状态、座位可用性，并防止同一学生在同一时间段重复预约。
预约成功或取消后发送站内通知。
管理员可以维护座位、查看预约记录，并在学生未到场或设备故障时取消预约。
系统需要记录预约状态、座位位置、取消原因和操作时间，并支持移动端查看。
```

## Voiceover Script

### 01. 开场

今天我们用一个很小的“图书馆座位预约系统”案例，完整走一遍 UML 实验平台的使用流程。你会看到从创建项目、选择免费托管模型，到输入需求、生成需求规则、生成 UML 和设计模型，再到代码原型和说明书交付。目标不是一次讲完所有理论，而是让你知道每一步点哪里、产出什么、下一步为什么依赖它。

### 02. 创建项目和选择 Provider

先进入项目首页，点击新建项目。项目是本次实验的工作空间，后面所有需求文本、模型、代码、运行历史和说明书都会沉淀在这里。项目名称填写“图书馆座位预约系统”，描述写清楚这是一个面向学生和管理员的座位预约课程实验。

这里的默认模型策略选择列表中的首个可用托管 Provider。你可以把它理解成老师或系统分配好的免费模型通道。后面抽取需求规则、生成 UML、生成代码和说明书，都会优先使用这个模型配置。如果项目没有单独设置，也可以在右上角账号入口的全局设置里选择托管 Provider 和默认模型。

### 03. 输入需求并生成规则

进入项目后，先来到需求页。把准备好的需求文本粘贴进去，然后点击生成需求规则。平台会把一整段自然语言需求拆成一条条结构化规则。每条规则会有编号、类型、文本内容和关联的目标模型。

需求规则很重要，因为它不是简单的摘要，而是后续 UML、设计模型、测试和说明书共同使用的输入契约。规则越清楚，后面的模型和代码越容易稳定。

### 04. AI 修复和人工编辑需求规则

生成完成后，我们看需求规则表。这里可以按类型筛选，也可以搜索规则。需求文本这一列可以直接修改，所以如果你发现某条规则太模糊，可以手动补上角色、触发条件、输入输出或异常处理。

如果规则旁边出现待确认提示，点开详情可以看到平台认为缺少什么。有些问题可以用智能修复生成候选结果。修复结果出来后，不要盲目采纳，先对比修复前后的文本和理由。觉得合理就采纳，不合理就拒绝，或者回到规则表自己改。新增需求项和删除需求项也在这里完成。

这一段要传达一个核心概念：AI 可以帮你修，但最终确认需求的人是你。只有规则确认好，后续模型才有可靠来源。

### 05. 生成需求 UML

需求规则处理好以后，选择要生成的需求阶段模型。常见的包括用例模型、领域概念模型、总体业务流程、部署需求模型、原型界面关系和需求分析模型。

点击生成 UML 后，可以打开顶部的生成任务观察进度。平台会经历抽取规则、生成结构化模型、生成 PlantUML、渲染 SVG 等阶段。如果缺少上游规则映射或前置模型，系统会尝试自动补齐，并在页面提示或运行记录中留下证据。录制时等待不用全放进视频，保留几秒让同学知道任务正在执行就够了。

### 06. 查看需求模型详情和手动校正

模型生成后，不要只看图片。打开一个模型详情页，比如用例模型或领域概念模型。这里可以查看 SVG 图，也可以看结构化的元素清单和关系说明。元素清单告诉你有哪些角色、用例、实体或节点；关系说明告诉你它们之间如何连接。

再看 PlantUML 或源码视图，它是 SVG 图的来源。追踪矩阵则回答“这个模型元素来自哪条需求规则”。如果图不准确，可以编辑元素或关系。确认编辑后，平台会保存当前模型草稿，并自动更新当前图。也就是说，模型既可以由 AI 生成，也可以由你人工校正。

### 07. 生成设计模型和映射规则

接下来进入设计页。设计模型是在需求模型基础上继续推导出来的。这里简单记住几条映射关系：用例模型通常会推导到用例实现设计和界面关系；领域概念模型会支撑设计类图和数据库设计；总体业务流程会帮助生成总体架构和组件关系；部署需求模型会继续推导部署设计。

选择需要的设计模型后点击生成设计模型。同样可以通过生成任务观察进度。如果设计阶段缺少某些需求阶段上游模型，平台也会提示或尝试补齐。

### 08. 查看设计模型详情

设计模型生成后，打开一个设计详情页。这里的查看方式和需求模型类似：先看 SVG，再看元素和关系，最后看追踪矩阵。区别是设计模型要回答“需求里的业务元素如何落到设计里的类、服务、数据库、组件和页面流程”。

如果你发现某个类名、关系或页面跳转不准确，也可以人工调整。调整后要注意，下游代码和说明书可能需要重新生成，才能使用最新设计。

### 09. 生成代码原型

进入代码页后，点击启动生成。代码页会根据设计模型和界面关系生成 React 原型。左侧可以看文件树，中间可以看具体代码，右侧或预览区可以查看生成出来的界面。

这里重点不是把代码当最终产品，而是用它快速验证页面流程和业务状态。例如查询座位、提交预约、重复预约提示、管理员维护座位等逻辑，是否已经在原型里体现。质量诊断会帮助你检查页面数量、组件结构和业务断言覆盖情况。

### 10. 生成和下载说明书

最后进入说明书页。这里可以生成需求规格说明书，也可以生成软件设计说明书。生成前可以打开说明书样式，调整标题、页眉、字号、目录等格式。

生成完成后，说明书会进入项目文档列表。你可以在项目中打开编辑器继续查看，也可以直接下载 DOCX。项目文档中心还会展示版本、下载状态和编辑锁状态，方便课程提交和后续复盘。

### 11. 收尾

到这里，我们已经完成了从需求到交付的主流程。回头看，需求文本变成了需求规则，规则生成了 UML，需求模型推导了设计模型，设计模型支撑代码原型和说明书。遇到失败时，可以从生成任务里看阶段和错误；需要复盘时，可以打开运行历史或链路图。这样一次实验不是只有结果文件，而是有完整的生成过程和可追踪证据。

## Recording Checklist

### 录制前

- [ ] 本地 Web/API/渲染服务可访问。
- [ ] 账号已登录，页面不显示敏感 API Key、个人隐私或无关项目。
- [ ] 全局设置或项目设置中已选择可用托管 Provider。
- [ ] Provider 连接测试成功。
- [ ] 示例需求文本已复制到剪贴板。
- [ ] 已准备一个空项目镜头和一个完成态项目镜头。
- [ ] 需求模型和设计模型至少各有一个成功渲染的 SVG。
- [ ] 代码预览非空。
- [ ] 说明书可以打开编辑器或下载 DOCX。

### 录制中

- [ ] 每个片段从稳定画面开始，鼠标静止 1 秒后再操作。
- [ ] 点击生成后只保留 3-5 秒任务进度。
- [ ] 长等待、错误重试和重复加载留给剪辑处理。
- [ ] 关键控件操作完成后停留 1-2 秒，方便后期缩放和配音对齐。
- [ ] 不展示浏览器密码管理、系统通知、聊天窗口或其它无关窗口。

### 剪辑后

- [ ] 总时长控制在 8-12 分钟。
- [ ] 旁白与画面操作同步。
- [ ] 关键按钮和表格文字在缩放后清晰可读。
- [ ] 生成等待段不超过 8 秒。
- [ ] 视频里没有 API Key、完整私人邮箱、无关项目名或敏感 URL。
- [ ] MP4 可正常播放，音量稳定。
- [ ] `.recordly` 工程、配音文件和导出视频已归档。

## Fallbacks

- Provider 临时不可用：录制仍展示选择首个可用配置的流程；生成结果使用预演成功的完成态项目补拍。
- OnlyOffice 编辑器未就绪：展示说明书页的“下载”或“下载当前 DOCX”能力，并说明项目内可查看，环境配置完整时可在线编辑。
- 生成任务失败：短暂展示错误和可重试入口，不在主视频里排查技术细节；切到完成态项目继续演示。
- 需求规则没有出现待确认项：手动修改一条规则，或新增一条有明显缺失的规则，用它演示智能修复和人工确认。
- 图过大不易读：以元素清单、关系说明和追踪矩阵为主，SVG 只展示整体效果。

## Acceptance Criteria

- 视频覆盖创建项目、选择托管 Provider、输入需求、生成需求规则、AI 修复、人工编辑、生成需求模型、模型详情、追踪矩阵、生成设计模型、设计详情、代码预览、说明书打开和下载。
- 旁白解释每一步的目的，不只描述“点击了什么”。
- 学生看完后能独立复现主流程，并理解需求规则、模型详情和说明书之间的关系。
- 成品视频和 Recordly 工程可被后续维护者复用，若产品界面变化，只需要补录对应片段。
